# Этап 2. Входящая карточка 112 и адресация ДДС

Реализовано 28.09.2026. Это отчёт о втором этапе, а не заключение о полной готовности всех требований ТЗ.

## Изменения

- Из рабочего потока исключены start_call, answer_call и end_call имитатора телефонии. Получение сообщения создаёт учебную карточку с provider=card112. Голос участника событий не генерируется.
- Преподаватель назначает обучающемуся службу из сохранённых версий ЕКП. Назначение доступно преподавателю и администратору; ученик не может менять его сам. Смена профиля во время активной карточки запрещена. Приём карточки и изменение профиля сериализованы блокировкой пользователя.
- В деталях пункта ЕКП добавлен конструктор сценария: название, адрес, описание, норматив, признаки, расчёт и проверка получателей.
- Исполняются явно распознанные условия always, flag и all_false. Отсутствующий признак не считается отрицательным. «Нет реагирования» не добавляет получателя.
- Неоднозначное условие, замечание исходной записи или изменение рассчитанных получателей требуют непустого пояснения преподавателя. Это явное учебное решение, не автоматическая расшифровка неизвестного алгоритма ЕКП.
- Сценарий хранит SHA-256 и идентификатор версии ЕКП, строку/лист/запись, код сценария реагирования, исходные правила с результатом проверки, выбранных получателей, автора и пояснение решения.
- Новый кабинет ученика показывает занятия с адресованными его службе карточками. Сервер проверяет профиль, группу, владельца карточки и роль. Старый endpoint получения также соблюдает адресацию новых карточек.
- Входящие тип, код ЕКП, адрес, описание, признаки и получатели доступны ученику для чтения. Доступны статус и комментарий. Попытка изменить исходные поля через API отклоняется.
- Таймер, восстановление активной карточки, базовая оценка, завершение занятия и PDF-отчёт работают с новым потоком. Эталоны и внутренние основания маршрутизации не передаются ученику.

Старые упражнения и URL calls сохранены для совместимости с данными и регрессионными тестами. Телефонный провайдер ими больше не вызывается. В интерфейсе преподавателя старый генератор свёрнут отдельно; при создании нового занятия через интерфейс предлагаются сценарии карточек ЕКП. Старые таблицы call_sessions и поля call_id пока сохранены без потери истории.

## Ошибки и замечания второго этапа

| Действие → ожидание → прежний результат → воспроизведение | Исправление / повторная проверка |
|---|---|
| Получить карточку → сообщение 112 → запуск mock-телефонии → старт любого старого упражнения | Провайдер звонка убран из sessions; provider=card112, API-цикл проходит |
| Войти под учеником другой ДДС → видеть адресованные своей службе карточки → профиль отсутствовал и доставка не фильтровалась → получить сценарий через calls/start | Профили и серверная фильтрация; чужой и пустой профиль не получают новую карточку |
| Заполнить работу ДДС → исходная карточка остаётся неизменной → ученик заново выбирал тип и службы → открыть прежний экран ученика | Новая карточка только для чтения; API запрещает SELECT_INCIDENT / SELECT_SERVICES / SELECT_TAGS для DDS_MESSAGE |
| Рассчитать получателей → учесть условия ЕКП → использовалась общая служба «ДДС» → создать сценарий старым генератором | Конструктор по записи ЕКП, проверяемые условия, явное пояснение по неопределённости |
| Отправить неизвестный статус через API → ошибка валидации → произвольная строка сохранялась → SELECT_STATUS со status=FAKE | Допустимые статусы проверяет сервер; повторный запрос даёт 422 |
| Менять профиль параллельно приёму → согласованный получатель → возможная гонка между назначением и выдачей | Общая блокировка пользователя, активная карточка блокирует смену; конкурентный стресс-тест отдельно не проводился |

Открытые задачи последующих этапов: полноценный список происшествий и журнал статусов; оценка последовательности событий вместо только последнего статуса; расширение статусов/карточки по скриншотам; нормы преподавателя и расширенный отчёт; итоговый ручной прогон. Сейчас базовый эталон нового сценария: последний статус ПРИНЯТО (2 балла) и непустой комментарий (1 балл). Статус «РАБОТЫ ЗАВЕРШЕНЫ» пока не заменяет этот эталон. Для демонстрации второго этапа используйте только ПРИНЯТО.

## Готовый сценарий демонстрации второго этапа

1. Открыть http://localhost:5173. Если уже выполнен вход, выйти или обновить страницу после изменения профиля.
2. Войти: **student@example.local / Student123!**. Профиль уже назначен: **Классификатор МВД** (точное имя из исходного XLSX).
3. Открыть занятие **«Этап 2 — получение карточки 112 службой МВД»**, нажать **«Получить карточку 112»**. Оно запущено, карточка оставлена непройденной.
4. Показать готовые сведения: ДТП без пострадавших, ЕКП 2010000, учебный адрес, описание и получателей. Звонка и голоса нет.
5. Выбрать **ПРИНЯТО**, написать «Информация получена службой.», сохранить комментарий. При желании обновить страницу: карточка и серверное начало отсчёта восстанавливаются.
6. В пределах 120 секунд нажать **«Завершить карточку»**. Ожидается 3/3; после превышения времени добавляется замечание о нормативе.
7. Выйти, войти **teacher@example.local / Teacher123!**. Найти результат, скачать PDF/CSV, завершить занятие.

Подготовка использует оригинальный импорт e0e407e4-524e-4250-bd4c-8f6392f682c5, строку 277. Условие V277 неоднозначно: в сценарии сохранено явно обозначенное учебное допущение преподавателя о направлении МВД, безусловные получатели оставлены. Это не утверждение о восстановлении полного внешнего алгоритма 2_4. Идентификаторы занятия и сценария — [stage2-demo-state.json](stage2-demo-state.json).

Для повторной демонстрации создайте новое занятие с тем же опубликованным сценарием: завершённая карточка повторно не выдаётся. Для нового сценария откройте ЕКП → выберите сохранённую версию → найдите происшествие → Открыть → заполните конструктор → Рассчитать получателей → проверьте и поясните решение → Сохранить сценарий карточки → Опубликовать → Создать занятие → Запустить.
